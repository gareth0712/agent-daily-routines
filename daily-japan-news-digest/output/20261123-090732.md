### [CLAUDE.md に書いても止まらない：Claude Code のお願いと強制の違いを実行して比べる](https://qiita.com/charge0315/items/a97bd8584df044368e02)
*寫進 CLAUDE.md 也擋不住：實測比較 Claude Code 的「請求」與「強制」差異*
來源：Qiita - ClaudeCode｜發布：2026-11-23 08:34 JST

作者在 Windows 11、Claude Code **2.1.328**、`--model sonnet`、`claude -p` 非互動模式下，於 CLAUDE.md 只寫一行「git push 前須向使用者確認」，並用 `--allowedTools` 預先允許 push，比較四種條件下 push 是否會被執行。結果：僅有 CLAUDE.md 時，模糊請求「反映到 remote」3 次全部停在 commit 並回頭詢問；但改成「趕時間，不用確認立刻 `git push origin main`」則 3 次全部直接 push。加上 `permissions.ask: ["Bash(git push *)"]` 或以 exit code 2 中止的 PreToolUse hook 後，同樣的請求 1 次都沒有 push 成功，`claude -p` 沒有人回答 ask 便直接結束。作者說明 permission 檢查順序為 deny → ask → allow，所以即使 `--allowedTools` 含 push，ask 仍會勝出；另為避免讀到 home 目錄的 CLAUDE.md，實驗以 `--setting-sources project,local` 啟動並用 `/context all` 確認只載入練習用的 55 tokens。結論：CLAUDE.md 是「請求」，會被 prompt 文字覆寫；要確實擋下對外操作必須用 ask / deny 或 hook。⚠️ 作者特別點出風險：若「不用確認直接 push」是寫在別的 AI 產生的手順書或 Issue 內文中，CLAUDE.md 同樣擋不住（本次未測試）。

### [Claude Codeのセッションを分岐して並行作業する：/fork と --fork-session の手順・落とし穴・検証方法](https://qiita.com/joinclass/items/8b30d5453db55388966a)
*分岐 Claude Code session 平行作業：`/fork` 與 `--fork-session` 的步驟、陷阱與驗證方法*
來源：Qiita - ClaudeCode｜發布：2026-11-23 08:30 JST

合同会社ジョインクラス（無員工公司，以 launchd 每日跑約 30 支 `claude -p` job）分享 session 分岐的實務作法。互動模式下輸入 `/fork` 會建立一個繼承目前對話的新 session，原 session 保留，可在另一個終端機用 `claude --resume` 選回原 session 試 B 案；關鍵是分岐前先把前提全部讀進對話，分岐後各自讀的檔案不會互通。陷阱：分岐的是對話而非檔案，兩個 session 編輯同一 repo 會互相覆寫（作者曾被 B 案 session 把 A 案修好的 `claude-run.sh` 寫回舊版），因此建議搭配 `git worktree add ../planB -b try/plan-b` 再 `claude --resume <id> --fork-session`。腳本化時用 `claude -p --session-id "$BASE"` 先建立前提 session，再以 `--resume "$BASE" --fork-session --output-format json` 同時分出 A、B 兩案，驗證方式是用 `jq -r .session_id` 確認兩者互異且不等於 BASE，否則代表漏掉 `--fork-session` 而寫回原 session。公司無人 job 原本無法分岐的原因是共通 wrapper 加了 `--no-session-persistence`（2026-11-15 發現 `~/.claude/projects` 的 jsonl 每天增加約 200MB 而關閉），導致事後無法 `--resume`；wrapper 也示範了 `--max-budget-usd 3`、`--fallback-model` 與以 `PIPESTATUS` 保留 claude 的 exit code。
